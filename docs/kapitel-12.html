Das solltest du schon kennen: alles aus den Kapiteln 1 bis 11, vor allem Exceptions und den Stacktrace aus Kapitel 11.

Eine Wetterstation misst jeden Tag die Temperatur und rechnet daraus Werte aus: den Höchstwert, die Frosttage, eine Warnung bei Sturm. Dieses Kapitel benutzt sie als Beispiel. Es geht aber um etwas anderes: Was tust du, wenn etwas rot wird?

Beim Programmieren ist Rot normal. Es heißt nicht, dass du etwas kaputt gemacht hast. Es heißt: Java zeigt dir eine Stelle, die noch nicht stimmt. Entscheidend ist, welche Art von Rot du vor dir hast. Jede Art bedeutet etwas anderes. Bei jeder gehst du anders vor.

Drei Arten von Rot

1. Rot unterstrichen: Java versteht den Code nicht

Woran du es erkennst
VS Code unterstreicht eine Stelle mit einer roten Wellenlinie, zum Beispiel return max. Fährst du mit der Maus darüber, erscheint die Meldung. Alle Meldungen auf einmal stehen in der Ansicht „Problems“ unten im Fenster.
Was das heißt
Der Code ist kein gültiges Java, zum Beispiel weil ein Semikolon fehlt. Java kann ihn nicht übersetzen. Das heißt: Der Code kompiliert nicht.
Was dann läuft
Nichts. Jeder Testlauf mit ./gradlew im Terminal übersetzt zuerst das ganze Projekt. Scheitert das an einer einzigen Stelle, läuft kein einziger Test. Auch die Tests von Aufgaben, die stimmen, laufen dann nicht. So sieht das im Terminal aus, wenn du einen Test aus Kapitel 7 startest, der Fehler aber in Kapitel 12 steckt (Pfad gekürzt):
> Task :compileJava FAILED
…/src/main/java/de/phl/crashkurs/k12/WeatherStation.java:23: error: ';' expected
        return max
                  ^
1 error
FAILURE: Build failed with an exception.

Startest du in VS Code einen Test, während etwas rot unterstrichen ist, fragt VS Code: Build failed, do you want to continue? (Das Übersetzen ist gescheitert, willst du trotzdem weitermachen?) Zur Wahl stehen „Continue“, „Always Continue“ und „Fix...“. Klick nicht auf „Continue“. VS Code startet die Tests dann trotzdem, und manche werden bei dir sogar grün. Mit ./gradlew läuft dagegen kein einziger Test, denn dort scheitert schon das Übersetzen. Behebe zuerst die rote Stelle.

2. Roter Test: Der Code läuft, aber das Ergebnis stimmt nicht

Woran du es erkennst
Nichts ist rot unterstrichen. Der Test startet, aber neben ihm erscheint ein rotes Kreuz statt eines grünen Hakens.
Was das heißt
Java versteht deinen Code und führt ihn aus. Nur liefert er für mindestens ein Beispiel nicht das, was der Test erwartet. Das ist ein Denkfehler, kein Schreibfehler.
Was dann läuft
Alle Tests. Die anderen Tests können grün sein.

3. Exception: Java bricht beim Laufen ab

Woran du es erkennst
Eine rote Meldung mit dem Wort Exception und darunter Zeilen mit at. Im Test ist der Test rot, und in seiner Meldung steht die Exception.
Was das heißt
Java versteht den Code, aber mit diesen Werten geht etwas nicht, zum Beispiel ein Fach, das es nicht gibt (Kapitel 11).
Was dann läuft
Alles bis zu der Zeile aus der Meldung. In einem Test wird nur dieser eine Test rot. Die anderen Tests laufen weiter.

So gehst du vor

Egal welche Art von Rot: Geh immer in derselben Reihenfolge vor. Das spart dir die meiste Zeit.

  1. Welche Art von Rot ist es? Ist irgendwo etwas rot unterstrichen, kümmerst du dich zuerst darum. Sonst läuft mit ./gradlew kein einziger Test.
  2. Die oberste Meldung zuerst. Ein einziger Fehler kann mehrere Meldungen auslösen. Die späteren verschwinden oft von selbst, wenn du den ersten behebst.
  3. Geh zur Datei und Zeile. In der Ansicht „Problems“ springt VS Code mit einem Klick auf die Meldung an die Stelle. Bei einer Exception steht die Zeile in der Klammer hinter at.
  4. Lies die Zeile und die Zeile davor. Oft liegt die Ursache eine Zeile höher. Ein fehlendes Zeichen fällt Java manchmal erst in der nächsten Zeile auf. Und bei einer Exception entsteht der falsche Wert oft eine Zeile, bevor Java abbricht.
  5. Ändere eine Sache, speichere, teste neu. Nicht drei Dinge auf einmal. Sonst weißt du nicht, was geholfen hat.

Ein roter Test: den Ablauf im Kopf verfolgen

Ein Denkfehler zeigt keine Meldung im Code. Du findest ihn, indem du den Code Zeile für Zeile durchgehst und an jeder Stelle fragst: Welchen Wert hat die Variable jetzt, und welchen sollte sie haben?

Das Programm unten soll die Regentage zählen: Tage, an denen mehr als 0 Millimeter Regen gefallen sind. In den drei Tagen hat es nur einmal geregnet. Die Antwort müsste also 1 sein. VS Code unterstreicht nichts. Klick dich durch die Fassung mit dem Fehler und schau, in welcher Zeile der Wert falsch wird.

Das Semikolon hinter der Bedingung in Zeile 4 beendet das if sofort (Kapitel 7). Der Block darunter gehört dann nicht mehr zum if und läuft in jeder Runde. Weder VS Code noch das Terminal melden hier etwas. Nur der Test wäre rot, weil 3 herauskommt statt 1. Klick zum Vergleich die behobene Fassung an.

Eine Testmeldung lesen

Ist ein Test rot, sagt dir seine Meldung genau, was er erwartet hat und was dein Code geliefert hat. So sieht die echte Meldung aus Aufgabe 2 dieses Kapitels aus:

org.opentest4j.AssertionFailedError: Bei -3, -7 und -1 Grad ist der Höchstwert -1. Mit welchem Wert startet max? ==> expected: <-1> but was: <0>
Der HinweisDer Text vor ==>. Den hat der Test geschrieben. Er nennt das Beispiel und gibt dir einen Tipp.
expected: <-1>„erwartet: -1“. Das ist das richtige Ergebnis.
but was: <0>„war aber: 0“. Das hat dein Code geliefert.

Die Werte in den spitzen Klammern sind der Schlüssel. Frag dich: Wie kommt mein Code auf 0? Dann gehst du den Code mit genau diesem Beispiel im Kopf durch, wie oben bei den Regentagen.

In VS Code findest du die Meldung beim roten Test: in der Ansicht „Testing“ (das Reagenzglas links) und im Bereich „Test Results“ unten. Im Terminal zeigt ./gradlew nur eine Kurzfassung, ohne den Text:

Kapitel 12, Aufgabe 2: WeatherStation > Höchstwert im Winter, alle Werte unter 0 FAILED
    org.opentest4j.AssertionFailedError at WeatherStationTest.java:20

Diese Kurzfassung nennt nur die Zeile im Test, nicht die Zeile in deinem Code. Die ganze Meldung siehst du in VS Code.

Eine zweite Testmeldung kennst du aus Kapitel 11: Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown. Der Test hat eine Exception erwartet, aber deine Methode hat keine geworfen.

Eine Exception verfolgen

Die Methode average rechnet den Mittelwert der Temperaturen aus: alle Werte zusammenzählen, dann durch ihre Anzahl teilen. Probier sie mit drei Messwerten und dann ohne Messwerte aus. Achte bei „keine Messwerte“ auf die Meldung und darauf, wohin die beiden at-Zeilen zeigen.

Die oberste at-Zeile zeigt auf WeatherStation.java, Zeile 7. Dort teilt Java durch temps.length, und das ist 0. Aber warum ist das Array leer? Das steht nicht in dieser Datei. Die zweite at-Zeile führt dich weiter: Main.java, Zeile 4 ruft average auf, und eine Zeile davor entsteht das leere Array. So gehst du einen Stacktrace Zeile für Zeile nach unten, bis du die Ursache findest.

Dieselbe Art von Meldung in einem Test

Passiert die Exception in einem Test, steht sie in der Meldung des Tests. Dann kommen noch mehr at-Zeilen dazu, die nicht zu deinem Code gehören. So sieht die echte Meldung aus Aufgabe 2 aus:

java.lang.ArrayIndexOutOfBoundsException: Index 4 out of bounds for length 4
	at de.phl.crashkurs.k12.WeatherStation.countFrostDays(WeatherStation.java:35)
	at de.phl.crashkurs.k12.WeatherStationTest.frosttage(WeatherStationTest.java:26)
	at java.base/java.lang.reflect.Method.invoke(Method.java:580)
	at java.base/java.util.ArrayList.forEach(ArrayList.java:1596)

Die Regel: Such die erste at-Zeile mit einer Datei, die du bearbeitest. Überspring alles mit java.base oder org.junit und die Testdatei (Name endet auf Test.java). Hier ist es WeatherStation.java, Zeile 35. Je nachdem, wo du die Meldung liest, stehen unten noch mehr solche fremden Zeilen. Wo der Fehler genau steckt, findest du in Aufgabe 2 selbst heraus. Denk an die Zeile davor.

Wenn du nicht fertig wirst: auskommentieren

Es kann passieren: Die Zeit wird knapp, und eine Methode ist halb fertig und rot unterstrichen. Dann gilt: Was nicht kompiliert, kommentierst du aus. Ein Kommentar ist Text hinter //. Java überliest ihn. So wird das Projekt wieder übersetzbar, und alle anderen Tests laufen.

Schreib dafür // vor jede Zeile. Oder markiere die Zeilen und wähle im Menü „Edit“ den Befehl „Toggle Line Comment“. Derselbe Befehl nimmt die // auch wieder weg.

Aber Vorsicht bei Methoden mit Rückgabewert (Kapitel 3). Kommentierst du alles zwischen den geschweiften Klammern aus, fehlt das return:

VS Code meldet dann: This method must return a result of type int. Das heißt: Die Methode verspricht ein int, gibt aber keins zurück. Schreib deshalb einen Platzhalter ans Ende, also ein return mit einem passenden Wert. Der Test für diese Methode bleibt rot, aber alle anderen laufen.

RückgabetypPlatzhalter
int, doublereturn 0;
booleanreturn false;
Stringreturn "";
eine Klasse oder eine Listereturn null;
voidnichts, eine void-Methode braucht kein return

Den Kopf der Methode (die erste Zeile) und die beiden geschweiften Klammern kommentierst du nie aus. Den Kopf ruft der Test auf.

Regeln für die Arbeit allein in VS Code

Sieben Regeln zum Merken

  1. Ist etwas rot unterstrichen, läuft mit ./gradlew kein einziger Test. Kompilieren geht vor allem anderen.
  2. Was du nicht fertig bekommst, kommentierst du aus. Bei Methoden mit Rückgabewert schreibst du einen Platzhalter wie return 0; hin.
  3. Vorgegebene Zeilen, Dateien und Tests änderst du nicht: keinen Methodenkopf, keinen Klassennamen, keine Testdatei.
  4. Nach jedem kleinen Schritt speicherst du und startest den Test.
  5. Bei einer Meldung: die oberste zuerst, dann die Zeile und die Zeile davor.
  6. Bei einem roten Test: Erwartet und geliefert vergleichen, dann den Code mit diesem Beispiel im Kopf durchgehen.
  7. Am Ende committest und synchronisierst du. Erst dann ist dein Stand auf GitHub angekommen.

Commit und Sync, Schritt für Schritt

Gespeichert ist noch nicht hochgeladen. Deine Änderungen liegen dann nur auf deinem Rechner. Auf GitHub kommt nur an, was du committest und synchronisierst. So lädst du deinen Stand hoch:

  1. Alles speichern. Im Menü „File“ auf „Save All“. Steht im Reiter einer Datei ein Punkt statt des ×, ist sie noch nicht gespeichert.
  2. Quellcodeverwaltung öffnen. Links in der Leiste das Symbol „Source Control“ anklicken, die verbundenen Kreise. Unter „Changes“ stehen alle Dateien, die du geändert oder neu angelegt hast.
  3. Nachricht schreiben. Oben ins Feld „Message“ kurz schreiben, was du gemacht hast, zum Beispiel Aufgabe 1 und 2 fertig.
  4. Committen. Auf den blauen Knopf „Commit“ klicken. Fragt VS Code There are no staged changes to commit. Would you like to stage all your changes and commit them directly?, klickst du auf „Yes“. Das heißt: Alle geänderten Dateien kommen in den Commit.
  5. Synchronisieren. Jetzt heißt der blaue Knopf „Sync Changes“, daneben steht ein Pfeil nach oben mit einer Zahl. Klick darauf. Erst damit lädst du den Commit zu GitHub hoch. Beim ersten Mal fragt VS Code This action will pull and push commits from and to "origin/main". (Das holt und lädt Commits von und nach GitHub.) Klick auf „OK“. In einem Codespace heißt der Knopf in Schritt 4 oft schon „Commit & Sync“. Dann passiert beides auf einmal.
  6. Prüfen. Unter „Changes“ steht nichts mehr, und der Knopf „Sync Changes“ ist verschwunden. Am sichersten öffnest du dein Repository auf GitHub im Browser und schaust, ob oben deine Nachricht beim letzten Commit steht.

Mach das nicht erst in der letzten Minute. Committe und synchronisiere nach jeder fertigen Aufgabe. Dann ist auch bei einem Absturz von VS Code das meiste schon angekommen.

Eine Einschränkung beim Üben: Das Übungsprojekt dieses Crashkurses gehört nicht dir, du hast es nur kopiert. Dort kannst du committen, aber nicht zu GitHub hochladen. Üb die Schritte 1 bis 4 also im Crashkurs. In deinen eigenen Repositorys, etwa bei den Übungen im Kurs, klappt auch Schritt 5.

Drei Fehler, bei denen kein Test läuft oder nichts ankommt

Kurz geprüft: Rot lesen

Bei den meisten Fragen geht es darum, eine Meldung der richtigen Stelle zuzuordnen. Lies zuerst die Meldung, dann den Code.

Jetzt reparierst du selbst: drei Aufgaben im Projekt

Diesmal schreibst du keinen neuen Code. Im Ordner src/main/java/de/phl/crashkurs/k12 liegen drei Dateien, die kompilieren, aber Denkfehler enthalten. In jeder Datei stecken genau zwei. Zu jedem Denkfehler gibt es einen eigenen Test, der rot ist, solange der Fehler drin ist. Ein paar Tests sind schon am Anfang grün. Die zeigen dir, welche Fälle schon stimmen.

  1. Starte den Test zur Aufgabe und lies die Meldung jedes roten Tests: Welches Beispiel, was erwartet, was geliefert?
  2. Lies die Beschreibung über der Methode. Sie sagt, was die Methode tun soll.
  3. Geh die Methode mit dem Beispiel aus der Meldung im Kopf durch, bis du die Zeile findest, an der der Wert falsch wird.
  4. Ändere nur diese Stelle, speichere, starte den Test. Ein roter Test weniger heißt: ein Fehler gefunden.

Achte auch auf gelbe Wellenlinien. Gelb ist kein Fehler, sondern eine Warnung: Der Code läuft, aber VS Code findet etwas verdächtig. Manchmal ist genau das der Denkfehler.
